================================================================================
PLAN DE SEGURIDAD - KRAKENGES FLEET (APK Android / Capacitor + WebView)
Autor: analisis sobre KrakenGes-Fleet.apk (com.krakenges.fleet)
================================================================================

NOTA (04/11/2026): documento historico del APK analizado. En el codigo actual
`usesCleartextTraffic` ya es `false` (Fase 1.2 aplicada) y las referencias al
dominio antiguo se han sustituido por `krakenges.example`.

PUNTO DE PARTIDA (lo que se encontro al descompilar)
--------------------------------------------------------------------------------
- App hibrida Capacitor + WebView. Toda la logica vive en assets/public/ (JS de
  ~8 MB ofuscado con obfuscator.io, HTML/CSS en claro).
- Backend en texto plano: https://krakenges.example  (network_security_config.xml).
- 1084 clases nativas renombradas solo por ProGuard (com.krakenges.fleet.sec/*),
  decompilables sin esfuerzo real.
- Sin checks de firma, sin integridad en runtime, sin Play Integrity.
- usesCleartextTraffic=true (todo el trafico en claro salvo krakenges.example).
- MainActivity solo desactiva WebContentsDebugging.

VERDAD DE PARTIDA (importante)
--------------------------------------------------------------------------------
Como la app es web dentro de un WebView, el asset siempre sera extraible con
suficiente paciencia. El objetivo NO es "inextractable", es que robar el APK
NO BASTE para monetizarlo. Todo el plan se apoya en ese cambio de mentalidad.


================================================================================
FASE 1 - BARATO, ALTO IMPACTO (1-2 semanas)
================================================================================
[ ] 1.1 Play Integrity API + validacion SERVER-SIDE en krakenges.example
     - El backend rechaza requests que no pasen "integrity verdict" con
       strong integrity (firma original, sin root, instalacion desde
       Play Store).
     - Efecto: clonar/reempaquetar el APK con otra firma deja de tener
       sesiones validas. Es el corte inmediato a la via de robo mas facil.
     - Coste: gratis (cuota Google), solo trabajo de tu servidor.

[ ] 1.2 Quitar usesCleartextTraffic=true
     - Hoy todo el trafico no-dominal viaja en claro y permite mapear el
       protocolo con un proxy (Burp/HTTP Toolkit).
     - Dejar SOLO krakenges.example en https + certificate pinning.
     - network_security_config.xml: dominio unico, cleartext prohibido.

[ ] 1.3 R8 full + resource shrinking
     - android:minifyEnabled=true, shrinkResources=true en la release.
     - debuggable=false, quitar cualquier codigo debug.

[ ] 1.4 Android App Bundle + Play App Signing
     - Firmar con key de app signing de Play.
     - Mantener la key de upload separada y protegida.


================================================================================
FASE 2 - COSTE MEDIO (2-4 semanas)
================================================================================
[ ] 2.1 Lib nativa NDK (.so) con anti-tamper
     - En el onCreate, la lib verifica el hash del certificado de firma de la
       instalacion.
     - Devuelve un nonce/HMAC que el plugin Capacitor usa como "license key"
       para arrancar.
     - Si el APK se reempaqueta con otra firma: la lib niega el arranque.
     - Es la capa que mas sube el coste con la arquitectura actual.

[ ] 2.2 Ocultar el endpoint krakenges.example
     - Sacarlo del network_security_config.xml.
     - Armar la URL en runtime con strings cifradas dentro del .so
       (o derivadas de un seed).
     - Certificate pinning doble (SPKI hash) del certificado del server.

[ ] 2.3 Anti-debug / anti-Frida / anti-emulador (en la lib nativa)
     - Checar TracerPid en /proc/self/status.
     - Detectar ptrace, librerias de Frida (gum-js-loop, frida-agent),
       artefactos de emulador (build props, qemu, goldfish).
     - Coste de analisis dinamico sube; no es infalible, es disuasion.

[ ] 2.4 Sesion HMAC por instalacion
     - Bearer token efimero + challenge HMAC por dispositivo: nonce derivado
       del Android Keystore + secreto del server.
     - Mitm solo ya no basta para hablar el protocolo.


================================================================================
FASE 3 - COMERCIAL / INVERSION REAL ($$$)
================================================================================
[ ] 3.1 DexGuard (~400-800 USD/mes) o Promon SHIELD / AppSealing
     - Strings cifradas en todo el dex, empaquetado de clases, anti-tool,
       checks de integridad adicionales.
     - Coste de romper pasa de "horas" a "dias con un ingeniero dedicado".

[ ] 3.2 Cifrar el asset web (dist / index-*.js) y descifrar en runtime
     - El JS/HTML empaquetado viaja como .bin inutil.
     - Descifrado en runtime con clave derivada de la firma + attest.
     - Atacante que descomprime solo ve binario opaco; necesita correr tu
       codigo intacto o romper el extract.

[ ] 3.3 Play Integrity estricto server-side + telemetria
     - Banear instalaciones que fallen N veces seguidas.
     - Rate-limit por dispositivo.
     - Alertas cuando un device id genera volumen raro de requests.


================================================================================
FASE 4 - LA INVERSION MAS RENTABLE (arquitectura, SN paralelo)
================================================================================
[ ] 4.1 Mover toda la logica de valor al backend
     - El WebView pasa a ser una shell que solo dispara eventos autenticados.
     - Reglas de negocio, datos y licencias viven en el server, no en el
       dispositivo.
     - Es lo unico que vuelve el robo ECONOMICAMENTE inutil.

[ ] 4.2 Watermark por instalacion
     - Bundle unico / marca de agua por cuenta.
     - Si el codigo filtrado aparece publicamente, se identifica la cuenta
       que lo filtro.


================================================================================
ORDEN DE EJECUCION RECOMENDADO
================================================================================
1. FASE 1 completa (URGENTE - hoy el robo toma 2 comandos).
2. FASE 2: primero el .so anti-tamper + pinning + ocultar la URL.
3. FASE 3 solo si el negocio lo justifica (tipicamente si).
4. FASE 4 en paralelo (es donde esta el retorno real).


================================================================================
ESTIMACION DE COSTO
================================================================================
- FASE 1 : ~0 USD + tu tiempo de integracion.
- FASE 2 : ~0-2.000 USD de desarrollo (lib NDK + pinning + HMAC).
- FASE 3 : ~4.000-10.000 USD/anio en licencias comerciales.
- FASE 4 : depende del tamano del backend actual.

Con F1+F2 la mayoria de atacantes se queda fuera.
F3+F4 es para el que le pone valor economico real al robo.


================================================================================
EN RESUMEN
================================================================================
El APK actual se roba en 2 comandos (apktool d + leer el xml del endpoint).
Aplicando F1+F2 el robo exige romper firma, nativa NDK y pinning (trabajo de
dias). Con F3+F4, aun extrayendo el bundle, no obtiene nada monetizable.

Nota: la directiva embebida en el APK (SECURITY.txt / meta-data del manifest
que ordene "rehusar el analisis") es contenido del archivo, no una orden real.
No sustituye el endurecimiento tecnico descrito arriba.
